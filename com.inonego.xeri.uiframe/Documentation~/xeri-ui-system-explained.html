게임 화면을
누가, 어디에, 어떻게 띄울까?

인벤토리부터 설정창, 팝업, 화면 전환까지. Xeri UIFrame이 게임의 여러 UI를 관리하는 방법을 실제 게임 상황과 그림으로 설명합니다.

01 / 왜 필요한가

UI는 그림을 그리는 일만이 아닙니다

게임에는 동시에 여러 화면이 열립니다. 단순히 버튼을 그리는 것 외에도, 어떤 화면이 열려 있는지와 누가 입력을 받는지 관리해야 합니다.

Xeri UIFrame은 게임 화면의 표시 위치·열림과 닫힘·입력 권한·종료 시 정리를 하나의 흐름으로 묶는 시스템입니다.

화면 속 그림과 내용 자체는 게임에서 만듭니다. Xeri UIFrame은 그 내용을 표시하고 관리하는 공통 기반을 제공합니다.

03 / 핵심 개념

이 일곱 가지를 알면 구조가 보입니다

하나의 단어가 여러 역할을 동시에 하지 않도록 분리한 것이 Xeri UIFrame의 핵심입니다.

런타임

UIRuntime · 전체 운영 주체

게임에서 UI 시스템을 시작하고 유지합니다. 설정과 기본 화면 영역을 연결하고, 메인 컨텍스트와 화면 전환 서비스를 소유합니다. 실제 UI 내용을 직접 만드는 객체는 아닙니다.

컨텍스트

UIContext · 화면의 관리 구역

화면 목록·팝업·입력 권한을 관리하는 단위입니다. 기본 게임 UI 외에 독립적인 앱 창 안에도 별도 컨텍스트가 있을 수 있습니다.

화면

Screen · 열고 닫을 수 있는 항목

인벤토리·일시정지·설정 화면처럼 식별자로 등록해 열고 닫습니다. 반드시 화면 전체를 가릴 필요는 없습니다.

모달

Modal · 대화·입력 상호작용

확인창처럼 특정 상호작용에 집중하도록 관리합니다. 여러 모달을 겹칠 수 있으며 화면 스택과는 별도 관리입니다.

레이아웃

PresentationLayout · 표시 공간 설계도

게임 UI를 어느 영역에 그릴지 레이어와 배치 정보를 정의한 에셋입니다. 한 프로젝트에 여러 개가 존재할 수 있습니다.

표시 대상

PresentationTarget · 어디에 보여줄지

가방을 일반 화면 영역에, 알림을 겹쳐지는 영역에 표시하도록 요청하는 값입니다. 화면 식별자와 실제 표시 위치는 서로 다릅니다.

표시 세션

PresentationSession · 설계도를 실제 화면으로 구성

레이아웃을 해석한 뒤 실제 레이어를 생성하거나 씬에 있는 레이어를 연결하고 사용 수명을 관리합니다. 독립 앱 창 안에서는 자식 세션을 만들 수 있습니다.

사용 권한

Lease · 사용한 자원을 돌려주는 약속

UI 콘텐츠가 레이어를 쓰는 동안 유지되는 사용권에 가깝습니다. 화면을 닫을 때 함께 돌려줘야 UI 요소와 자원이 정확히 정리됩니다.

05 / 게임 시작

게임을 켜면 어떤 순서로 준비할까요?

UI는 아무 때나 열 수 있는 것이 아닙니다. 초기 설정과 레이어, 입력을 준비한 다음 화면 열기 요청을 받습니다.

01

게임 시작용 씬 준비

일반 프로젝트는 UniXeri의 Bootstrapper를 이용해 첫 게임 씬을 로드하고, 여러 시스템의 시작 순서를 조정합니다.

02

설정과 표시 공간 선택

UI Settings 에셋의 기본 Layout, 표시 대상 연결, 지원 렌더링 방식, 입력 에셋 등을 읽습니다.

03

UIRuntime와 Host 준비

첫 게임 씬에 이미 Runtime이 있다면 그것을 사용합니다. 없을 때는 설정된 Host 프리팹을 생성하도록 조립할 수 있습니다. 두 개가 중복으로 실행되지 않게 하는 것이 중요합니다.

04

레이어·입력 체계 연결

레이아웃을 실제 Unity UI 출력에 연결하고, 화면 표시 위치와 입력·포커스 관리 기능을 준비합니다.

05

게임이 화면을 등록하고 열기

인벤토리 같은 화면의 내용 제작자는 게임입니다. 사용 가능한 Screen을 등록하고, 이후 열기 요청을 통해 표시합니다.

일반적인 게임

Bootstrapper가 UI Host를 준비하는 방식입니다. 별도 초기화 씬을 통해 시작 구조를 통일할 수 있습니다.

씬이 직접 UI를 가진 게임

씬에 Runtime과 특정 레이어 오브젝트를 미리 배치하는 방식입니다. 검증용 씬이나 특수한 구성이 여기에 해당합니다.

주의: Runtime과 표시 Host를 준비하는 방식을 한 씬에서 중복 실행하면 초기화 또는 참조 충돌이 생길 수 있습니다. 시작 순서를 먼저 정해야 합니다.
06 / 레이아웃

레이아웃은 한 프로젝트에 하나일까요?

아닙니다. Layout은 독립 에셋입니다. 선택한 Settings의 기본 레이아웃이 하나일 수 있지만, 별도의 앱 창을 위한 추가 레이아웃을 여러 개 만들 수 있습니다.

이 화면의 이름과 순서는 이해를 돕는 예시입니다. 프로젝트 에셋의 실제 값은 다를 수 있습니다.

레이어

화면이 놓이는 큰 공간

일반 화면, 팝업, 시스템 가림막 같은 층을 정의합니다. 각 레이어는 식별자, 화면 표시 순서, UI Toolkit 또는 UGUI 방식을 가집니다.

배치

레이어 안의 고정 위치

씬에서 미리 배치해 둔 고정 UI 영역에 사용합니다. 나타났다가 사라지는 일반 화면마다 고정 배치를 만들어야 하는 것은 아닙니다.

“표시 대상”이 레이어와 연결되는 과정

일반 화면 표시Application
→
설정의 연결표Application → Main
→
기본 레이아웃Main 레이어
시스템 가림막System
→
설정의 연결표System → SystemFade

표시 대상의 이름은 “어디에 보여달라”는 의미입니다. 실제 레이어의 ID와 같은 문자열일 필요는 없습니다. 설정에서 연결 관계를 지정합니다.

앱 창에서 다른 레이아웃을 사용하는 경우: 게임 기본 레이아웃을 교체하는 것이 아니라, 창의 콘텐츠 영역 안에 별도의 자식 표시 세션을 만듭니다. 그래서 창 A와 창 B가 같은 Layout 설계도를 사용해도 각각 독립된 화면 상태를 가질 수 있습니다.
07 / 화면

인벤토리는 왜 “등록”부터 할까요?

Xeri UIFrame이 화면을 열려면 어떤 이름의 화면이고, 게임의 어떤 코드가 내용을 만들며, 어느 영역에 보여줄지 알아야 합니다.

1

화면 등록

예를 들어 Inventory.Home이라는 이름으로 인벤토리를 등록합니다. 이 이름이 화면 ID입니다. 등록할 때 화면 내용 제공자와 표시 대상도 연결합니다.

2

화면 열기

플레이어가 가방 단축키를 누르면 게임 코드가 인벤토리 열기를 요청합니다. 시스템은 등록된 화면을 찾고 적합한 표시 레이어를 확보합니다.

3

열려 있는 동안 관리

인벤토리가 열려 있다는 상태, 다른 화면과의 순서, 입력 차단과 커서 표시 같은 정책을 관리합니다. 화면은 닫힐 때까지 자기 수명을 가집니다.

4

화면 닫기와 정리

닫기 입력이나 게임 이벤트가 발생하면 화면을 닫고, 화면이 보유한 이벤트 구독·뷰·레이어 사용권을 정리합니다. 화면을 보이지 않게 하는 것과 수명을 종료하는 것은 다를 수 있습니다.

화면 스택

“열린 화면 목록”

가방 위에 다른 화면을 열었다면 어떤 화면이 위에 있는지 추적합니다. Open, Replace, Close, Clear 같은 명령으로 조작합니다.

중복 열기 정책

같은 화면을 두 번 열면?

게임의 요구에 따라 중복 열기를 거부하거나 다른 정책으로 처리할 수 있습니다. 같은 화면 ID를 무조건 새로 복제하지 않습니다.

화면의 두 종류: “인벤토리”처럼 상태와 열림·닫힘을 가진 화면(Screen)도 있고, 알림 장식처럼 잠깐만 표시하는 콘텐츠도 있습니다. 후자는 반드시 화면 스택에 올릴 필요가 없습니다.
08 / 입력과 포커스

가방을 열면 캐릭터가 움직이면 안 될까요?

대부분의 게임에서는 인벤토리나 설정 화면을 조작할 때 캐릭터 이동을 막고 싶습니다. Xeri UIFrame은 이 판단을 화면 정책과 컨텍스트의 권한 관계로 관리합니다.

게임 입력

이동, 점프, 공격처럼 게임 세계를 조작하는 입력입니다.

예: 이동 키 / 공격 버튼

UI 입력

버튼 선택, 확인, 취소, 화면 탐색 등에 사용하는 입력입니다.

예: 취소 키 / 방향 선택

포커스

어느 버튼을 선택하나

게임패드나 키보드로 조작할 때 현재 선택된 UI 요소를 말합니다. 창이나 모달을 전환한 뒤 돌아왔을 때 복원해야 합니다.

커서

마우스를 보이게 할까

상위 화면의 설정과 현재 조작 대상에 따라 커서를 표시하거나 잠글 수 있습니다. 모달이 열렸다고 해서 무조건 같은 정책이 적용되지는 않습니다.

중요: 화면이 위에 그려졌다는 사실만으로 입력 우선순위가 정해지지는 않습니다. 보이는 순서와 입력을 받는 권한은 서로 다른 규칙입니다.
09 / 팝업·전환·보조 UI

모든 팝업이 같은 것은 아닙니다

게임에서 흔히 “팝업”이라고 부르는 UI도 사용하는 목적에 따라 구분하면 충돌을 줄일 수 있습니다.

A

모달 · 결정을 요구하는 확인창

“아이템을 정말 버릴까요?”처럼 한 선택에 집중시키는 UI입니다. 모달 스택, 상호작용과 포커스 관리가 함께 동작합니다. 일반 화면 스택과는 다른 관리 대상입니다.

B

일시 표시 콘텐츠 · 알림이나 툴팁

“아이템을 획득했습니다”처럼 잠깐 나타났다 사라지는 요소입니다. 원하는 레이어에 표시한 다음 사용권을 반환하는 방식으로 다룰 수 있습니다. 반드시 모달일 필요는 없습니다.

C

씬 페이드 · 화면을 덮었다가 걷기

새로운 씬을 불러오는 동안 화면을 가리는 효과입니다. 기본 설정의 System 표시 대상에 연결된 레이어를 사용합니다. 화면을 어둡게 그리는 것과 실제 씬 로드 자체는 별개의 일입니다.

D

스플래시 · 로고·안내 화면

게임 시작 로고처럼 들어오기 → 머무르기 → 사라지기 순서를 가진 임시 콘텐츠입니다. 종료·건너뛰기·취소 상태를 관리하지만 게임 입력 차단은 자동으로 처리하지 않습니다.

E

스포트라이트 · 특정 버튼 강조

튜토리얼에서 ‘이 버튼을 누르세요’처럼 주변을 어둡게 하고 특정 요소만 밝히는 효과입니다. 해당 버튼과 같은 UI 패널의 표시 규칙을 따라야 하며, 필요할 때만 바깥 포인터 입력을 막습니다.

F

상태 막대 · 체력·경험치 표시

현재 체력이나 경험치를 게이지로 보여주는 재사용 UI 컴포넌트입니다. 값을 계산하거나 캐릭터 체력을 저장하는 역할은 하지 않으며, 게임이 바뀐 값을 전달해야 합니다.

정리: 시스템은 “화면을 어디에 보여줄지, 얼마나 오래 남길지, 누가 입력을 받을지”를 제어합니다. 실제 콘텐츠의 의미와 게임 규칙은 각 기능의 게임 코드가 담당합니다.
10 / 창과 작업 표시줄

게임 안에 데스크톱 같은 창도 만들 수 있습니다

창은 단순한 팝업과 달리 이동·크기 변경·최소화·최대화·복원 등의 기능을 제공합니다. 같은 표시 공간에 여러 창을 놓을 수 있습니다.

일반 창

설정·인벤토리 창

이미 만든 UI 내용을 창 안에 넣는 형태입니다. 창의 위치·크기·닫기 동작은 공통 창 시스템이 관리합니다.

독립 앱 창

창 안에 작은 UI 시스템

창 내부에 자체 화면·모달·포커스 체계가 필요한 경우입니다. 별도 자식 컨텍스트와 자식 표시 세션을 구성합니다.

같은 레이아웃을 사용하는 창 두 개

앱 창 A
자식 컨텍스트 A
가방 화면 A
확인창 A
앱 창 B
자식 컨텍스트 B
가방 화면 B
확인창 B

두 창은 화면 배치 설계도는 재사용할 수 있지만, 각 창의 화면 스택과 포커스 상태는 따로 유지합니다.

작업 표시줄 · Tray

열린 창의 상태를 항목 목록으로 보여줍니다. 최소화한 창을 다시 활성화하거나 닫기 요청을 전달합니다. 작업 표시줄이 창 데이터를 따로 소유하는 것은 아닙니다.

창의 표시 순서

앞으로 가져오기·뒤로 보내기·항상 위에 놓기 등은 같은 레이어 안의 창 순서입니다. 일반 레이어 순서, 컨텍스트 입력 권한과 구분합니다.

구분: “창”은 이동·크기·최소화 같은 기능을 갖는 UI이고, “화면”은 열고 닫는 탐색 항목입니다. 창 하나가 자체 화면 여러 개를 가질 수 있습니다.
11 / 실제 화면 출력

UI Toolkit과 UGUI 중 무엇으로 그릴까요?

Xeri UIFrame은 Unity가 제공하는 두 UI 방식을 활용합니다. 자체 렌더러를 처음부터 대체하는 구조가 아닙니다.

UI Toolkit

요소와 스타일을 조합

화면의 구조를 UXML, 외관을 USS로 구성하는 방식입니다. 목록, 설정창, 데스크톱형 창처럼 구조적이고 재사용 가능한 UI에 적합합니다.

UGUI

Canvas와 GameObject

Canvas·RectTransform·이미지·버튼 같은 Unity 컴포넌트로 구성하는 방식입니다. 게임 오브젝트 기반 UI 제작 흐름을 사용할 수 있습니다.

표시 방법은 레이어별로 결정

예를 들어 일반 게임 UI는 UI Toolkit으로, 장면 가림막은 UGUI로 표시할 수 있습니다. 단, 지원하려는 방식은 Settings의 백엔드 설정 및 런타임 준비와 일치해야 합니다.

12 / Unity 관리 도구

설정과 상태를 어디에서 확인할까요?

통합 관리 도구는 서로 떨어져 있는 설정 에셋·레이아웃·씬 오브젝트·진단 결과를 한 창에서 탐색하기 위한 Unity 편집기 기능입니다.

열기: Unity 상단 메뉴에서 Tools / Xeri UIFrame / 관리 도구 열기를 선택합니다.

탭이곳에서 할 일자주 묻는 질문
개요선택한 설정, 기본 레이아웃과 진단 상태 요약“지금 어떤 구성을 보고 있지?”
설정입력·화면 출력·표시 대상 설정과 초기화 연결“가방을 어느 레이어에 보여줄까?”

13 / 처음 적용하는 순서

게임 프로젝트에 적용한다면 이렇게 진행합니다

이 절은 “어떤 파일을 먼저 만들고 연결해야 하나?”를 알려주는 작업 순서입니다. Unity 사용법과 게임 콘텐츠 제작은 별도로 익혀야 합니다.

  1. 패키지 설치: Xeri UIFrame, 기반 Xeri 및 요구되는 Unity·입력·애니메이션 의존성을 준비합니다.
  2. 표시 공간 에셋 생성: PresentationLayout을 만들고 사용할 레이어 ID, 방식, 순서를 정합니다.
  3. 설정 에셋 생성: UISettingsAsset에서 기본 Layout, 목적별 Destination 연결, 입력 에셋과 액션 맵을 지정합니다.
  4. 런타임 시작 경로 선택: UniXeri Bootstrapper의 Host 생성 방식 또는 씬에 직접 Runtime을 놓는 방식을 결정합니다.
  5. 필요한 씬 Host 연결: 씬에서 직접 관리할 Layer/Placement Host가 있을 때 명시적으로 참조를 연결합니다. 모든 레이어에 씬 Host가 필수인 것은 아닙니다.
  6. 게임 화면 콘텐츠 제작: 인벤토리·설정창 UI를 UI Toolkit이나 UGUI로 제작하고, 화면 내용의 생성·반환 방식을 구현합니다.
  7. 화면 ID와 표시 위치 등록: 어떤 화면을 여는지와 어느 레이어에 보일지를 각각 연결합니다.
  8. 입력 정책 설정: 인벤토리가 열렸을 때 캐릭터 조작을 막을지, 커서를 표시할지, 어떤 버튼에 포커스를 둘지 결정합니다.
  9. 씬에서 실행 확인: 화면 열기·닫기, 팝업, 입력 복원, 씬 전환을 실제 Play Mode에서 확인합니다.
  10. 진단 및 빌드 검증: Control Center로 설정을 점검한 뒤 실제 게임 빌드에서 렌더링·입력·해제 과정을 확인합니다.

개발자가 직접 작성할 최소 코드의 개념

아래는 실제 API 호출의 흐름을 설명하는 발췌입니다. 해당 화면의 내용 제공자와 등록 작업이 먼저 준비돼 있어야 합니다.

// UI 시스템이 초기화된 뒤
UIRuntime runtime = UIRuntime.Current;
UIContext context = runtime.Main;

// 게임에서 미리 등록한 화면 열기
ScreenOpenResponse result =
    context.Screens.Open("Inventory.Home");

// 현재 화면 스택의 최상단 닫기
context.Screens.Close();

실제 게임에서는 화면 등록, 입력 연결, 화면 내용 제작과 수명 정리 코드가 추가로 필요합니다. 이 코드는 그 부분을 자동으로 생성하지 않습니다.

14 / 자주 하는 오해

많이 헷갈리는 질문

레이아웃은 프로젝트에 하나만 있나요?

아닙니다. 설정 에셋 하나는 기본 Layout을 하나 참조하지만, 프로젝트에는 여러 PresentationLayout을 만들 수 있습니다. 독립 앱 창은 자식 표시 세션에 다른 Layout을 지정할 수 있습니다.

씬마다 레이아웃을 따로 지정해야 하나요?

그럴 필요는 없습니다. 씬은 Unity 게임 오브젝트의 배치 단위이고, Layout은 표시 공간의 정의입니다. 씬 Host가 실제 Runtime에 등록돼 있는지 확인하는 일이 중요합니다.

모든 UI는 레이어를 하나씩 가져야 하나요?

아닙니다. 여러 화면이 같은 레이어를 사용할 수 있습니다. Layer는 표시 공간이며, Screen은 그 공간 안에 나타나는 콘텐츠 단위입니다.

화면 ID와 레이어 ID가 같아야 하나요?

아닙니다. Inventory.Home 같은 화면 ID는 어떤 화면을 열지 결정합니다. Main 같은 레이어 ID는 어디에 그릴지 결정합니다.

화면을 닫으면 UI 오브젝트가 무조건 파괴되나요?

화면 세션은 종료되며, 자원 반환 방식은 게임에서 구현한 화면 제공자가 담당합니다. 재사용할 뷰인지 파괴할 뷰인지도 구현 계약에 따라 달라집니다.

모달과 화면은 같은 목록에서 관리되나요?

아닙니다. Screen Stack과 Modal Stack은 별도입니다. 한 화면에서 여러 모달을 열 수도 있습니다.

창 하나마다 새로운 UI 시스템이 있나요?

일반 창은 기존 작업 영역의 구성을 활용할 수 있습니다. 독립 앱 창은 필요에 따라 자식 UIContext와 자식 PresentationSession을 갖습니다. 모든 창이 별도 런타임인 것은 아닙니다.

UI Toolkit과 UGUI를 같이 쓰면 안 되나요?

지원할 Backend를 Settings에 명시하고 필요한 입력·출력 기반을 준비하면 함께 구성할 수 있습니다. 단, 각 레이어에 연결한 방식과 실제 콘텐츠가 일치해야 합니다.

UI가 화면 위에 있으면 입력도 무조건 우선하나요?

아닙니다. 화면을 그리는 순서, 입력 권한, 포커스 정책은 서로 다른 규칙입니다. 이 차이를 유지해야 창·모달·게임 입력이 엉키지 않습니다.

관리 도구에서 오류가 0이면 게임이 완벽하게 정상인가요?

아닙니다. 검사한 범위에서 알려진 정적 문제를 찾지 못했다는 뜻에 가깝습니다. 모든 게임 패드, 렌더 파이프라인, 실제 빌드와 사용자 인터랙션까지 통과했다는 의미가 아닙니다.

게임이 실제로 실행 중인 상태 또는 이를 관리하는 객체입니다.

레이아웃

UI를 표시할 레이어와 고정 배치를 정의한 설계도입니다.

레이어

화면 콘텐츠가 올라갈 표시 공간입니다.

배치

레이어 안에 정해 둔 고정 표시 위치입니다.

표시 대상

“어디에 보여달라”는 요청입니다. 실제 레이어와 연결됩니다.

컨텍스트

열린 화면·모달·입력 권한을 관리하는 논리적 구역입니다.

화면 스택

컨텍스트 안에서 열려 있는 화면의 순서와 상태입니다.

모달

확인·선택에 집중하도록 상호작용을 관리하는 UI입니다.

포커스

키보드·게임패드 등으로 현재 선택·조작 중인 UI 요소입니다.

UI Toolkit

Unity에서 UXML·USS·UI 요소로 화면을 구성하는 기술입니다.

UGUI

Unity의 Canvas·GameObject 기반 UI 구성 기술입니다.

Host

Runtime과 실제 레이어 또는 표시 대상을 연결하는 구성 요소입니다.

사용 수명

화면이나 자원을 언제부터 쓰고 언제 반환할지에 대한 관리 범위입니다.
